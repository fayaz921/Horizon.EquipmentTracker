- (event) bmad-product-brief started from client input docs/00-client-input.md
- (fact) Client is Horizon Survey Services, Lahore; 25 staff, 14 field surveyors
- (fact) Tech stack fixed: .NET 9 Web API, EF Core, SQL Server LocalDB, React Vite TypeScript, Bootstrap
- (override) Removed ungrounded assumptions: 'low digital literacy', 'equipment hoarders', QR/kiosk, and offline connectivity are not requirements
- (gap) Contradiction in input: Voice note says 'anyone can take anything', but follow-up email restricts the drone to Hamza's approval
- (gap) Undecided policy: Follow-up email leaves approval requirement for the new GPS rover explicitly undecided ('I will decide later')
- (decision) Selected working mode: Coaching path; user decides all requirements, one question at a time
- (decision) Per-item RequiresApproval flag + named ApproverId; Drone=on/Hamza, others=off, New Rover=off by default (configurable in UI); restricted items enter 'pending approval' state until approved
- (decision) Hybrid checkout: surveyors self-serve passwordless by selecting name + item (trust model); Saima can log/correct on behalf of anyone; store both recipient and logged_by; Approvers use a PIN for authorizing restricted items
- (decision) Two inventory types: individually tracked (unique row/status/holder) and counted/bulk (total qty, available = total minus out). Checkouts support multiple independent lines. Kits are saved templates pre-filling lines, not owning entities
- (decision) Mandatory expected return date at checkout (default today; Today/Tomorrow/custom). Returns require condition selection (Good vs Damaged + optional note). Damaged items transition to 'Needs Inspection' and cannot be checked out until cleared by Saima/Owner. Counted items track damaged quantity decrementing available count
- (decision) In scope: Overdue/Due-Today badges + one-click wa.me WhatsApp reminder button with pre-filled message; Person entity stores phone number. Out of scope: Automated WhatsApp Business API (deferred/future)
- (decision) History: on-screen table with Last Month/This Month/Custom presets; filter by person/item; overlap date matching (still-out spans to today); no CSV export in v1; soft-delete/deactivation for records. Admin actions (clear damage, toggle approval, CRUD people/equipment) protected by shared Admin PIN
- (decision) Database auto-seeds on first run via EF migrations: sample people (Tariq, Saima, Hamza, sample surveyors), equipment (sample serialized + 4 tripods, 6 tablets, new rover with approval=off), kit template, demonstrable checkouts (1 overdue, 1 last month). Demo PINs in appsettings.json, hashed, documented in README
- (decision) Item availability rules: items out, pending approval, or in Needs Inspection cannot be checked out; counted items cannot be checked out beyond available count
- (decision) Approval lifecycle: pending approvals remain pending until Hamza acts (no auto-approval timeout); original requester can cancel pending request
- (decision) Return mechanics: per-line returns including partial returns for counted items; due dates can be extended by holder or Saima with audit trail of extensions
- (decision) Equipment lifecycle: added 'Lost' status settable exclusively by Admins behind Admin PIN
- (decision) Scope prioritization: Must-have (checkout/return, who-has-what screen, overdue tracking, damage block, history); Should-have (approval flow, counted items, kit templates, WhatsApp links); Cut/Out-of-scope (automated WhatsApp API, CSV export, real logins). UI mobile-first, timezone Pakistan Standard Time (PKT / UTC+5)
